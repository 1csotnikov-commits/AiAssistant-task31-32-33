# RAG: индексация, поиск и ответ

## Как устроен RAG

RAG в `AiAssistant` состоит из пяти шагов:

1. **Сбор файлов.** `iter_source_files()` берёт `README.md`, все `docs/**/*.md`,
   `docs/**/*.yaml|yml|json` и Python-файлы `ai_assistant/**/*.py`.
2. **Чанкинг.** Markdown режется по заголовкам, Python — по функциям, классам и
   методам; слишком длинные секции делятся на окна по 60 строк.
3. **Индексация.** Чанки пишутся в SQLite FTS5 с токенизатором `unicode61`.
4. **Retrieval.** Вопрос превращается в FTS5-запрос; возвращается top-K
   фрагментов (5 для задач 31 и 33, 5 docs + 5 code для задачи 32).
5. **Генерация.** DeepSeek получает вопрос, фрагменты с путями и строками,
   git-контекст; ответ дополняется детерминированным блоком «Источники».

## Формат чанка

```text
id, path, title, kind (doc|code), start_line, end_line, text
```

Пример id: `docs/rag.md:14-48`. Для кода заголовок — имя функции/класса или
`Class.method`.

## Чанкинг Markdown

- заголовок `# ... ######` начинает новый чанк;
- `title` — текст заголовка, `start_line` — строка заголовка;
- вступление до первого заголовка получает имя файла;
- секция длиннее 80 строк делится на части по 60 строк с суффиксом
  «(продолжение)».

## Чанкинг Python

- `ast.parse` выделяет top-level функции, классы и методы;
- для класса создаётся чанк-заголовок и отдельные чанки методов
  (`Index.search`);
- декораторы включаются в чанк;
- при синтаксической ошибке используется fallback — окна по 60 строк.

## Схема FTS5

```sql
CREATE VIRTUAL TABLE chunks_fts USING fts5(
    id UNINDEXED, path UNINDEXED, title, kind UNINDEXED,
    start_line UNINDEXED, end_line UNINDEXED, text,
    tokenize='unicode61'
);
```

Ранжирование — `bm25(chunks_fts)`, чем меньше значение, тем релевантнее.

## Поисковый запрос и fallback

`_fts_query()` извлекает слова, добавляет префиксные варианты для длинных слов
(например, `авториз*` находит «авторизация» и «авторизации») и соединяет их
через `OR`. Если FTS5 не дал результатов или запрос не разобрался, выполняется
case-insensitive поиск по `LIKE` с ранжированием по числу вхождений.

## Инкрементальная переиндексация

Для каждого файла считается SHA-256. При повторном `aiassist index`:

- совпавший хэш → файл пропускается (`без изменений`);
- новый/изменённый хэш → старые чанки удаляются, новые вставляются;
- исчезнувший файл → удаляется из `files`, `chunks` и `chunks_fts`.

`--force` игнорирует хэши. Индекс не хранится в Git.

## Prompt и цитаты

Системный prompt требует:

- отвечать по-русски;
- использовать только предоставленные фрагменты и git-контекст;
- при отсутствии ответа написать «В документации этого нет»;
- не ссылаться на файлы, которых нет во фрагментах.

Блок источников формируется кодом, а не моделью, поэтому цитаты стабильны:

```text
Источники:
- docs/architecture.md → «Компоненты»
- README.md → «Назначение»
```

Если чанков нет, LLM не вызывается: возвращается `NO_CONTEXT_ANSWER` и пустой
список источников. Это защищает от галлюцинаций.

## Ограничения

Лексический поиск не понимает синонимы без общих корней и сложные перефразы.
Для MVP это осознанный компромисс: нет embeddings, векторной БД и локальных
моделей, зато индекс строится быстро и полностью локально.
